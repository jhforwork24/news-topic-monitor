# 일간 예약 루틴 — 편집·감사·발행 절차

연결된 Claude의 일간 예약("일간 브리핑 자동 편집·감사·발행")이 매일 수행하는 절차의 정본이다.
예약 프롬프트와 서브에이전트 지시는 이 문서를 가리키며 **날짜·ID 같은 매개변수만** 넘긴다.
편집 기준은 [`claude-editorial-instructions.md`](claude-editorial-instructions.md), 감사 기준은
[`claude-auditor-task.md`](claude-auditor-task.md), 장애 대응은 [`operations.md`](operations.md)가
정본이며 이 문서는 그 문서들을 어떤 순서로 호출하는지만 정한다.

## 우선순위

1. `AGENTS.md`의 필수 규칙이 가장 우선한다. 프롬프트도 문서도 이를 완화할 수 없다. 발행 게이트·
   독립 감사 fatal·final-state를 우회하지 않고, 유료 API 같은 승인 사항은 사용자 승인 없이 쓰지
   않는다. 같은 문서의 "사전 승인 범위"에 든 작업(`allow_stale_revalidation`, 조건부 `force`,
   발행 후 사실 오류 정정 등)은 묻지 않고 수행하되 사후 보고한다. PR 생성·병합은 사전 승인
   범위가 아니다.
2. **절차와 기준은 `main`의 최신 문서가 프롬프트보다 우선한다.** 예약이 실행될 때마다 이 문서와
   위 두 지침을 GitHub `main`에서 새로 읽는다(캐시한 사본이나 이전 대화의 기억을 쓰지 않는다).
3. 프롬프트는 **매개변수**(실행 날짜, Notion data source·페이지 ID, queue_id 등 이번 실행에만
   해당하는 값)와 **이번 실행에 한정한 사용자 지시**만 정한다. 프롬프트가 문서와 다른 절차를
   적고 있으면 문서를 따르고, 그 불일치를 보고사항에 남겨 한쪽을 고치게 한다.
4. 새로 알게 된 반복 패턴은 대화에만 남기지 말고 지침 문서를 고치는 PR로 남긴다.

## 비밀·식별자 규칙

Notion data source ID, 페이지 URL, token은 이 저장소(문서·코드·fixture·로그)에 쓰지 않는다
(AGENTS.md). 문서는 데이터소스를 이름으로만 부른다 — 대기열·초안·감사는 `대기열 초안 감사 등`,
최종 브리핑은 `언론 보도 브리핑` 계열 data source, 정정 기록은 `브리핑 정정 이력`. 실제 ID는 예약
프롬프트의 매개변수 블록에만 둔다.

## 매개변수 (프롬프트가 넘기는 값)

| 이름 | 의미 |
|---|---|
| `report_date` | KST 기준 오늘 날짜 `YYYY-MM-DD`. 예약이 깨어난 시각을 KST로 바꿔 구한다 |
| 대기열 data source | `대기열 초안 감사 등`의 ID |
| 브리핑 data source | 최종 브리핑이 올라가는 data source의 ID (발행 확인용) |

조사 구간은 매개변수가 아니라 코드(`_report_window`)가 정한다. 직전 발행일 05:00 KST 경계부터
당일 05:00 KST까지이며, 화요일만 토요일 경계까지 내려가 72시간(토·일 보도 포함)이다. 날짜별
길이를 미리 짐작하지 않고 매니페스트의 범위를 그대로 따른다.

## 절차

### 1단계 — 대기열 확보

1. `대기열 초안 감사 등`에서 `Claude 편집 대기열 · {report_date} · 매니페스트`를 찾는다. 있으면
   2단계로.
2. 없으면 기다리지 말고 `editorial-queue.yml`을 workflow_dispatch로 직접 실행한다
   (`date={report_date}`, `dry_run=false`). **`force`는 기본으로 쓰지 않는다** — 기존 대기열을 버리고
   새 queue_id를 만들어 이미 작성된 초안을 무효화한다. 대기열 자체가 망가졌고(후보 합계 불일치,
   손상된 묶음 등) 해당 날짜 브리핑이 아직 발행되지 않았을 때만 쓰며, 쓰면 사유를 보고한다. 뒤늦게 발동한 예약 실행이 겹쳐도 매니페스트가
   있으면 `already_built`로 아무것도 하지 않는다([`operations.md`](operations.md) "대기열이 제때
   없을 때").
3. 2분 간격으로 완료를 확인한다. 평소 10~15분(시간초과 재시도가 돌면 몇 분 더), 화요일은 더
   걸릴 수 있다. 화요일 35분, 그 외 요일 25분이 지나도 끝나지 않거나 실패하면 실패 job 로그로
   원인을 진단해 사용자에게 보고하고 중단한다(원인 후보: `CHAT_EDITORIAL_BRIDGE_ENABLED` 변수,
   출처 수집 실패 등).
4. 완료되면 매니페스트를 다시 찾는다. 매니페스트의 `출처 점검` 절을 읽어 편집자에게 전달한다
   (아래 서브에이전트 호출 규칙).

### 2단계 — 편집 초안 (독립 서브에이전트 1)

`general-purpose` 서브에이전트를 하나 띄운다. 호출 템플릿은 아래 "서브에이전트 호출 규칙"을
따른다. 에이전트는 [`claude-editorial-instructions.md`](claude-editorial-instructions.md)를 그대로
따라 `Claude 편집 초안 · {report_date}`를 제출한다.

### 3단계 — 독립 감사 (독립 서브에이전트 2)

편집 초안이 끝난 뒤 **새로운 Agent 호출**로 별도 서브에이전트를 띄운다. 편집 에이전트와 컨텍스트를
공유하지 않는다. [`claude-auditor-task.md`](claude-auditor-task.md)를 그대로 따르고
`Claude 독립 감사 · {report_date}`를 제출한다. 감사의 `draft_id`는 초안과 정확히 같아야 하고
`submitted_at`은 초안보다 늦은 실제 KST 시각이어야 한다.

### 4단계 — fatal finding 처리

findings에 fatal이 없으면 5단계로. 있으면 이 세션이 해당 후보의 근거 원문을 대기열에서 직접
확인해 finding이 지적한 문제만 최소 수정한다.

- 이슈를 통째로 빼거나 새로 지어내지 않고 서술을 근거 범위 안으로 좁힌다. 근거가 이슈 적격
  기준 자체를 못 채우거나 유일한 근거가 저비중+칼럼 제외 기준에 해당하면 이슈 제외도 최소 수정에
  포함한다.
- 고정 칼럼·인사 소식 미처리 지적은 해당 후보를 알맞은 섹션에 넣거나 `plan.exclusions`에 이유를
  남겨 해소한다. 비마이너 오피니언은 제외 사유로 면책되지 않는다.
- 발행 검증이 "허용 범위 밖의 칼럼이 포함됨"으로 막으면 해당 이슈를 `opinion`에서 빼고
  `plan.exclusions`에 사유를 남긴다. 대기열이 칼럼으로 판정하지 않은 외부 필자 기고는 매체가
  허용 목록에 있어도 `opinion`에 넣을 수 없다.
- 수정 뒤 `draft_id`/`submitted_at`을 새 KST 시각으로 갱신해 초안 페이지를 고치고, 감사 페이지의
  findings를 그 항목만 재검증해 비우거나 그대로 둔다. 감사 제출시각은 갱신한 초안보다 늦어야 한다.
- 스스로 판단하기 애매하거나 명백히 해소되지 않는 fatal은 통과시키지 말고 **발행을 보류**하고
  사용자에게 구체적으로 보고한다.

### 5단계 — 발행

fatal이 없는 상태가 확인되면 `editorial-finalize.yml`을 workflow_dispatch(`date`, `dry_run=false`)로
실행하고 완료(5~10분)까지 확인한다.

- 성공: 최종 브리핑 data source에 오늘 브리핑이 생겼는지, `health/publish_gate/latest.json`이
  `allowed=true`인지 확인한다.
- 실패: 실패 job 로그로 원인을 진단한다. 알려진 패턴이면 최대 2회까지 재시도한다.
  - 외부 사이트 robots.txt 시간초과 등 일시적 네트워크 오류 → 코드 수정 없이 단순 재시도.
  - 고정 칼럼 미처리 → 4단계 방식으로 초안을 고친 뒤 재시도.
  - "보고 경계가 8시간 이상 지나 …재검증할 수 없음" → `allow_stale_revalidation=true`로 재시도한다
    (사전 승인). 발행 본문에 재검증 지연 사실이 공개 고지되므로, 지연 사유와 함께 사후 보고에 반드시
    포함한다. 재시도 전에 지연이 컨테이너 재시작 같은 일시적 원인인지, 초안·감사 시각이 어긋난
    탓인지(위 "시각" 규칙)부터 확인한다 — 시각 문제는 플래그로 풀리지 않는다.
  - "이슈 요약에 언론사를 언급함"(발행 검증) → 해당 이슈의 `summary`에서 매체명과 "○○은 …라고
    보도했다" 문형을 걷어내 사안 요약으로 고치고(4단계 방식, 근거 범위 안에서만) 재시도한다. 매체별
    보도 방식은 `tone_analysis`에 이미 있는지 확인한다.
  - 처음 보는 코드 결함으로 보이면 우회하지 말고 구체적 진단과 함께 보고한다.

## 서브에이전트 호출 규칙

### 공통

- 프롬프트에는 `report_date`, 매니페스트·후보 묶음·초안 페이지 ID, `queue_id`, 후보 수, 필요하면
  `draft_id`만 넣는다. 절차와 기준은 문서를 읽게 한다. 이 문서 자체도 읽게 한다.
- 매니페스트를 먼저 읽고 `출처 점검`에 적힌 사실(수집 실패, 시간초과 후 복구, 승인된 robots 예외)을
  에이전트에게 요약해 알린다. 수집 실패를 기사 부재로 해석하지 않는다.
- 후보 묶음은 순번과 후보 합계가 매니페스트와 일치하는지 검증한다. 화요일은 후보가 최대 360개까지
  늘 수 있고 이는 이상 신호가 아니다. 섹션 상한은 창 길이와 무관하게 그대로다.
- notion-fetch 결과가 토큰 초과로 파일에 저장되면 `Read`의 offset/limit이 아니라 Bash(python)로
  파싱한다. 후보 본문은 `{"candidates":[…]}` JSON이므로 `json.JSONDecoder().raw_decode`로 읽는다.
- **시각은 반드시 `TZ=Asia/Seoul date -Iseconds`로 확인한 실제 시각을 쓰고, 지금 시각보다 앞서
  적지 않는다.** 실제보다 5분 넘게 앞서면 제출이 거부되며, 5분 이내라도 final-state 판정이 어긋난다:
  finalize의 공식 재수집은 감사 `submitted_at` 뒤에 이뤄진 것만 인정하므로, 감사 시각을 아직 오지
  않은 시각으로 적으면 재수집이 "감사 완료 전"으로 판정돼 진행형 이슈가 전부 `final-state revalidation이
  COMPLETE가 아님`으로 막힌다(2026-10-03). 제출 시각을 적은 뒤에 finalize를 실행하고, 이미 막혔다면
  시각이 지난 뒤 내용 수정 없이 다시 실행하면 된다. `draft_id`는 `draft-{날짜 숫자}-HHMMSS`다.
- 제출 페이지의 제목과 `날짜` 속성(`report_date`, 날짜형)을 반드시 채우고, 제출 뒤 다시 읽어
  제목·날짜 속성·`queue_id`·`draft_id`·JSON code block이 **정확히 1개**인지 확인한다.
- 한국어를 `\uXXXX` 이스케이프로 손으로 쓰지 않는다. 평문 한국어로 쓴다.
- 서브에이전트는 최종 브리핑을 발행하지 않는다.

### 호출 템플릿

서브에이전트 프롬프트는 아래 틀에 값만 채운다. 절차와 기준은 문서가 정본이므로 틀에 옮겨 적지
않는다. 괄호는 대기열 data source의 페이지 ID 등 이번 실행의 값이다.

편집:

```
report_date={report_date}. GitHub main의 docs/daily-routine.md "서브에이전트 호출 규칙"과
docs/claude-editorial-instructions.md를 읽고 그대로 따라 'Claude 편집 초안 · {report_date}'를
제출하라. 최종 브리핑은 발행하지 않는다.
- data source: {대기열 data source ID}
- 매니페스트: {page id}, queue_id={queue_id}, 후보 {N}개 / {M}묶음
- 후보 묶음 page id: 01={..}, 02={..}, …
- 출처 점검 요약: {매니페스트 "출처 점검" 절의 요지}
```

감사:

```
report_date={report_date}. GitHub main의 docs/daily-routine.md "서브에이전트 호출 규칙"과
docs/claude-auditor-task.md를 읽고 그대로 따라 'Claude 독립 감사 · {report_date}'를 제출하라.
편집자의 보고는 모른다. 최종 브리핑은 발행하지 않는다.
- data source: {대기열 data source ID}
- 매니페스트·후보 묶음: 편집과 같음
- 초안: {page id}, draft_id={draft_id}, submitted_at={값}
```

감사 템플릿에는 편집 에이전트의 보고 내용(선정 이유, 판단이 애매했던 지점)을 넣지 않는다.

### 편집 서브에이전트

- `movement-position-canon` 스킬을 요약 작성 전에 로드한다.
- 이슈 요약 구성은 편집 지침을 따른다. `summary`는 언론사를 언급하지 않는 사안 요약, `tone_analysis`는
  매체별 보도 방식이다. **호출 프롬프트에 "매체명을 주어로 쓴다" 같은 지시를 따로 넣지 않는다.**
  2026-10-01·10-02 발행본에서 요약 첫 문단이 거의 모두 매체를 주어로 쓴 것은 호출 프롬프트의 그런
  문구가 원인으로 보인다(9/29·9/30 발행본은 대부분 매체를 쓰지 않았다).
- 후보 전수를 검토하고, 힌트가 붙은 후보(`III절 고정 칼럼`, `III절 비마이너 오피니언`,
  `인사 소식 감시 대상`, `II절 비지정 매체`)의 처리 규칙은 편집 지침을 따른다.
- 완료 보고에 선정 건수(섹션별, 노동은 하위 주제별), 힌트 후보 처리 결과(`candidate_id` 포함),
  `draft_id`, 판단이 애매했던 지점을 포함한다.
- 감사에서 반복적으로 fatal이 된 서술 패턴을 피한다: 근거에 없는 게재면·기고 성격 단정, 기사 본문의
  서술을 인물 발언으로 귀속, 한 매체 근거를 다른 매체로 확대 귀속, 서로 다른 사건의 병합.

### 감사 서브에이전트

- 편집자의 보고나 판단을 읽지 않고 대기열 원자료와 초안만 처음부터 대조한다.
- 힌트 후보는 초안 보고를 믿지 말고 대기열 전수에서 직접 검색해 대조한다.
- 완료 보고에 findings 개수와 심각도, 각 finding의 `candidate_id`·이슈 제목·핵심, 힌트 대조 결과,
  발행 가능 여부 판단을 포함한다.

## 보고 원칙

평소에는 조용히 진행한다. 다음의 경우에만 KST 시각과 함께 사용자에게 보고한다.

- (a) 발행 성공 — 게이트 warning과 감사 warning이 있으면 함께 알린다.
- (b) 대기열이 끝내 생성되지 않음.
- (c) fatal finding을 자체적으로 해소하지 못해 발행을 보류함.
- (d) finalize가 2회 재시도 뒤에도 실패함.
- (e) 처음 보는 새로운 버그로 보이는 실패.
- (f) 사전 승인 범위의 작업(`allow_stale_revalidation`, `force`, 발행 후 정정 등)을 실행함 — 한 일, 이유,
  근거, 결과를 알린다. 같은 상황이 반복되면 원인을 함께 짚는다.

예약 실행 중의 `send_later` 자체 체크인은 사전 승인 범위에 들지만, 아직 예약 환경에서 승인 프롬프트
없이 도는지 확인하지 못했다. 프롬프트가 뜨면 예약 시각에 아무도 승인하지 못해 파이프라인이 멈추므로,
시험으로 확인되기 전까지는 쓰지 않고 막힌 지점과 다음에 확인할 항목을 보고사항에 남긴다. PR 생성·병합과
`AGENTS.md`가 승인을 요구하는 작업(유료 경로, 새 출처 robots opt-in, census 축소)은 예약 안에서 스스로
하지 않고 보고한다.
